# Fix: Docker DB migration on startup

## Problem

The Dockerfile in your screenshot has **two `CMD` lines**:
```dockerfile
CMD ["bun", "run", "db:push"]
CMD ["bun", "run", "dev", "--host", "0.0.0.0"]
```

Docker only uses the **last** `CMD`. So `db:push` is silently skipped — your schema changes never get applied when the container starts.

## Current state

- `docker-compose.yml` mounts `.:/app` (source code overlay) and `/app/node_modules` (named volume)
- `local.db` lives on the host filesystem
- `db:push` = `drizzle-kit push` — compares schema.ts to the DB and alters it to match. It's idempotent and safe to run repeatedly.
- You've been running `db:push` manually on your host before starting the container

## Why you don't need to rebuild on every schema change

With the volume mount (`.:/app`), the container always sees your latest source code. Schema changes are reflected immediately — no rebuild needed. The only thing missing is **running `db:push`** to sync the DB.

## Fix

Create an entrypoint script that runs `db:push` then starts the dev server:

### 1. Create `entrypoint.sh`
```bash
#!/bin/sh
set -e
bun run db:push
exec bun run dev --host 0.0.0.0
```

### 2. Update Dockerfile
```dockerfile
FROM oven/bun:1 AS base

WORKDIR /app

COPY package.json bun.lock* ./
RUN bun install

COPY . .
RUN chmod +x entrypoint.sh

EXPOSE 5173

CMD ["./entrypoint.sh"]
```

### 3. No docker-compose.yml changes needed

The volume mount already handles source code. `db:push` runs inside the container but modifies the host's `local.db` through the mount.

## Why this works

- Every container start: schema is synced automatically
- `db:push` is idempotent — if schema is already current, it's a no-op (~100ms)
- No rebuild needed for code or schema changes
- Data persists in `local.db` on the host

## Files to modify

- `Dockerfile` — single CMD pointing to entrypoint
- `entrypoint.sh` — new file, runs db:push then dev
